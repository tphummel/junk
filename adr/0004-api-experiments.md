# 0004: How API experiments are built

- Status: Accepted
- Date: 2026-11-14

## Context

All APIs run in one Cloudflare Worker (`api/index.ts`, a [Hono](https://hono.dev) router) at `https://junk.tomhummel.com/api/*`; static files are served from `web/` (`assets.run_worker_first` is `["/api/*"]`). The first routes (`health`, `golden-angle-palette`) established the conventions below, so that agent sessions add routes consistently. The Worker is public and shares one deploy.

## Decision

1. **One file per experiment.** `api/<name>.ts` default-exports a Hono sub-app with routes relative to its mount point (`app.get("/:color", ...)`). `<name>` is lowercase kebab-case, and the same as the paired `web/<name>/` if there is one.
2. **Register it** in `api/index.ts`: one import and one `app.route("/api/<name>", sub)` line, in alphabetical order. Unknown paths fall through to the global JSON 404.
3. **JSON in, JSON out.** Validate all input before using it. Bad input returns `400` with `{ "error": "<message>" }` where the message says what to use instead. Never return stack traces.
4. **HTTP behavior is chosen per API and stated in its sub-app:** `GET` for read-only calls; `Cache-Control: public, max-age=…` only when the response is deterministic; CORS (`hono/cors`) only when browsers on other origins should call it.
5. **Public by default.** There is no authentication. Anything that must be protected needs its own ADR (for example Cloudflare Access or a token check) before it ships.
6. **Tests.** `api/<name>.test.mjs` using `node:test` and `app.request()` (no network): the happy path, every validation error, and any headers the API promises. `npm test` runs `api/**/*.test.mjs`; CI runs `npm run types`, `npm run typecheck` and `npm test` on PRs.
7. **Types.** TypeScript, checked by `npm run typecheck`. `worker-configuration.d.ts` is generated by `npm run types` and is gitignored.
8. **Shared logic.** Code used by both a page and its API is a plain ES module under `web/<name>/` that the API imports (ADR 0002). Wrangler bundles it into the Worker.
9. **Bindings and secrets.** Declare bindings (KV, D1, R2, Durable Objects) and vars in `wrangler.jsonc`. Previews do not inherit production settings, so every binding or var also needs a matching entry in `previews` pointing at test resources, never production ones. Secrets are never committed: `wrangler secret put` for production, `.dev.vars` locally.
10. **Verify in the PR preview** (`https://<branch>.junk.tomhummel.com/api/<name>/...`) before merging.

The step-by-step procedure, code and test templates, and the checklist for bindings are in the [`new-api-experiment` skill](../skill/new-api-experiment/SKILL.md).

## Consequences

- Adding an API is one file, one test file and one registry line; nothing else in the Worker changes.
- All APIs share one deploy: a type error or a failing build blocks every experiment, and bindings are shared across them.
- `api/index.ts` is a registry that parallel sessions will conflict on; keep both entries.
- Every API is public, including any it adds that write data.
- Previews need their own test resources for every binding, which must be created by hand.

## Alternatives considered

- **One Worker per API.** Better isolation and independent rollbacks, but a route and a config per API, which suits a junk drawer poorly.
- **Colocating each API in its project folder.** Considered early on; a flat `api/` keeps the registry and tests in one place.
- **Plain `fetch` handler with path matching.** Fewer dependencies, but sub-routers, params and middleware are what Hono is there for.

## Open (needs its own ADR when first needed)

- **Storage.** Which of KV, D1, R2 and Durable Objects to use, and whether APIs share a binding with per-app key or table prefixes or get dedicated ones. A shared binding lets any API read any other's data.
- **Authentication** for any API that should not be public.
